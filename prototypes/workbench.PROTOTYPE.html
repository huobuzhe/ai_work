这台草模要回答什么

把一句话变成一个可复用按钮，中间到底该经过几步？ 状态模型是 理解 → 解释与影响预览 → 用户确认 → 执行 → 命名参数化固化 → 下次一键复用； 「动作配方」被暂定成 功能种类 + 命名参数 + 产物介质 + 步骤 四件事。

请边点边问：哪一步是多余的？哪一步缺失了？顺序对不对？特别留意三处「拦住了」和最后那次「一键运行」—— 它们就是让「动作配方」「解释与影响预览」「固化为按钮」这几个词变得可争论的地方。答案要记回票 #4 的反馈。

分支假设（写在最前面，便于推翻）： /prototype 有 UI 与 LOGIC 两支。本仓库目前没有应用、没有路由约定、没有组件库， UI 支要求的「把变体挂到既有页面 / 按项目路由新建 throwaway route」都落不了地；而票 #4 要的反馈是「哪些步骤多余 / 缺失 / 顺序不对」， 属于状态机而非版式。因此这里做 LOGIC 支：一个自包含 HTML、一个可搬走的纯 reduce(state, action) 模块、 自由试按按钮 + 四个导览场景。若你其实想比较三种工作台版式，说一声，我再用 UI 支另做一版 ?variant= 的。

什么是真的、什么是假的：表格与「对应文件」是内存里的假数据；「理解」只是关键词匹配，不是 LLM； 公式只认 字段 op 字段/数字；没有读写任何 xlsx、没有连飞书 / 腾讯文档、没有网络请求、没有持久化。 按研究笔记的结论，真实版本要自己补「自然语言解释 → 结构化配方编译与保存」这一环，这里故意留成假的。
